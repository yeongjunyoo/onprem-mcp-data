## 프로젝트 세부 내용

### 개발배경 및 목적

기업이 사내 데이터에 AI를 붙이려 할 때 두 가지가 동시에 걸린다. 첫째, 모델과 서비스마다 연동을 따로 만들어야 하고 청킹과 임베딩 설정 중 하나만 어긋나도 정확도가 무너진다. 둘째, 사내 데이터는 외부 API로 내보낼 수 없다.

이 프로젝트는 두 문제를 한 번에 풀기 위해 MCP를 연동 표면으로 삼고, 모델과 데이터베이스를 전부 사내에 두는 구성을 택했다. 목표는 세 가지다.

1. 연동 지점을 MCP 서버 한 곳으로 모아 장애 지점과 설정량을 줄인다.
2. 질문의 성격에 맞는 도구를 사람이 고르지 않고 시스템이 고른다.
3. 단순화가 품질을 깎지 않는다는 것을 튜닝이 아니라 측정으로 보인다.

### 개발환경

- 언어와 런타임: TypeScript 5.9, Node.js 20 LTS
- MCP 프레임워크: air(@airmcp-dev/core 0.2.0), 도구 정의는 defineServer와 defineTool
- 데이터 저장소: PostgreSQL 16, pgvector 0.6.0, primary와 streaming replica 구성
- 모델 런타임: Ollama 0.32.4. 생성 모델 qwen2.5:7b(Apache-2.0, Q4_K_M), 임베딩 모델 bge-m3(MIT, 1024차원)
- 컨테이너: Docker Compose가 PostgreSQL(pgvector, 호스트 5433)과 Ollama(호스트 11435)를 기동한다. MCP 서버는 `full` 프로파일의 선택 서비스이며 **stdio 전송**이라 TCP 포트를 열지 않는다. 읽기 복제본은 별도 스파이크 스크립트로 검증했고 상시 구성이 아니다. 서버 Dockerfile 빌드 검증 완료
- 외부 통신: 없음. 코드 전체에서 접근하는 원격 주소는 **로컬 Ollama뿐**이며, 이는 CI 검사(`scripts/verify-no-external-api.mjs`)로 강제한다 — 루프백이 아닌 대상이 생기면 빌드가 실패한다. 기본값은 `localhost:11434`(호스트 설치)이고, `docker compose`로 띄우면 `localhost:11435`다. 어느 쪽이든 루프백이며 외부로 나가지 않는다. 실행 시작 시 실제로 붙은 엔드포인트를 찍는다.
- 테스트: 자체 러너 기반 단위와 통합 테스트 417단언 전량 통과(오프라인 290 + DB·모델 127). 집계 원자료 `eval/results/test-counts.json`

### 시스템 구성 및 아키텍처

질문이 들어오면 다음 순서로 흐른다.

1. **라우팅**: 규칙 기반 라우터가 질문 어휘와 스키마, 그래프 온톨로지를 대조해 structured, semantic, knowledge_graph 중 하나 이상을 고른다. LLM 호출이 없고 튜닝 파라미터가 없으며 재실행 결과가 바이트 단위로 같다.
2. **병렬 조회**: 선택된 레인이 동시에 실행된다. structured는 스키마 카드를 받은 NL2SQL이 읽기 전용 가드를 통과한 SQL만 실행하고, semantic은 pgvector 코사인 검색, knowledge_graph는 양방향 BFS로 관계를 따라간다.
3. **융합**: RRF로 레인별 결과를 하나의 후보 목록으로 합친다. 리스트마다 같은 키를 한 번만 가산하도록 고쳐, 연결 수가 많은 그래프 허브가 교차 소스 합의를 이기는 문제를 제거했다.
4. **큐레이션**: 후보를 구조를 보존한 형태로 잘라 컨텍스트를 만든다. 표는 표로, 관계는 관계 문장으로 남긴다.
5. **생성**: 로컬 7B 모델이 컨텍스트 안의 근거만으로 한국어 답변을 만든다. 컨텍스트에 없는 개체가 답에 등장하지 않도록 접지 규칙을 강제하고, 질문이 지목한 개체를 온톨로지에서 해소하지 못하면 컨텍스트를 비우고 모른다고 답하게 한다.

MCP 도구는 **8개**를 노출한다 — `route`, `sql.query`, `vector.search`, `retrieve`, `ask`, `audit.explain`, `ontology.search`, `graph.expand`. 도구별로 위험도 계층을 표기했고, 계층 구분은 지정과제 필수 참조인 Pylon-7 연구의 정의를 따랐다. (KG 검색은 `retrieve`/`ask` 안에서 도는 내부 단계이지 별도 노출 도구가 아니다.)

### 프로젝트 주요기능

**핵심 기능과 특장점**

- **세 갈래 자동 분기**: 사업자가 공개한 예시 질문 30문항에 대해 도구 라벨 일치 30/30, 20회 재실행 결과 동일. 라우터 어휘는 라벨이 아니라 스키마와 그래프 온톨로지에서 뽑았다. 다만 이 30문항은 공개된 예시이므로 일반화 수치가 아니라 분기 의도 일치의 확인으로 읽어야 한다.
- **구조 보존 큐레이션이 정확도의 결정 레버**: 같은 데이터, 같은 모델, 같은 채점기에서 스키마 카드를 준 경우와 테이블명만 준 경우의 NL2SQL 실행 일치가 6/10 대 2/10으로 갈렸다. 실패 8건 중 6건이 존재하지 않는 컬럼을 지어내는 유형이었고, 값 어휘까지 담은 스키마 카드를 주면 그 실패군이 사라진다. 재시도를 한 번 허용하면 8/10 대 7/10으로 좁혀지고 대신 재시도 횟수가 2회 대 6회로 갈린다.
- **환각 차단 게이트**: 데이터셋에 없는 회사명을 물으면 관계 전체를 컨텍스트에 밀어 넣는 대신 0건과 명시적 not found를 반환한다. 답변에 등장한 데이터셋 개체가 컨텍스트를 벗어난 사례는 0건이었다.
- **장애 지점 축소**: 데이터베이스 정지, 지연, 부분 실패를 주입하는 스위트에서 무중단 4/4, 부분 응답 4/4, 오류 가시성 4/4를 기록했다. 읽기 엔드포인트는 primary 정지 시 replica로 넘어가며, 실제 프로세스를 죽이는 kill drill 로그를 저장소에 남겼다.
- **오픈소스 준수**: 직접 작성한 코드는 Apache-2.0, 의존 패키지 110개는 전부 허용형 라이선스이며 카피레프트 의존성이 0건이다. 자재명세는 설치된 매니페스트에서 자동 생성한다.

**구동 및 시연**

- `docker compose up -d`로 PostgreSQL(5433)과 Ollama(11435)를 올리고, `docker compose exec ollama ollama pull qwen2.5:7b` / `bge-m3`로 모델을 받는다. 호스트에 Ollama가 이미 있으면 포트가 충돌하므로 컨테이너는 11435로 분리했다.
- `npm run companyx:load`가 공식 데이터셋을 원본 DDL 그대로 적재한다. 8테이블 818행, 문서 40건을 258청크로 분할, 그래프 133노드 354엣지, 그래프 노드와 관계형 행을 잇는 브릿지 133건이다. 데이터셋은 배포 조건상 저장소에 포함하지 않고 취득 스크립트와 SHA-256 명세로 재현한다.
- `npm run demo:ollama`는 네트워크 없이 도구 8종 호출부터 답변 생성, 장애 주입까지 한 번에 보여준다. 기반 데이터나 모델이 없으면 성공으로 끝내지 않고 무엇을 해야 하는지 알리고 멈춘다.
- 평가 재현은 `npm run companyx:route`, `companyx:sql`, `companyx:kg`, `companyx:vector`, `companyx:ask`로 각각 실행하며 결과는 `eval/results/`에 JSON으로 남는다.

### 기대효과 및 활용분야

사내 데이터에 AI 검색을 붙이려는 조직은 대개 문서 검색, 통계 조회, 관계 추적을 별도 시스템으로 갖는다. 이 구조는 셋을 하나의 MCP 서버 뒤로 넣고, 클라이언트는 도구를 고르지 않아도 된다. MCP를 지원하는 어떤 클라이언트든 서버 주소만 알면 붙는다.

온프렘 전제를 지켰기 때문에 개인정보나 계약 정보처럼 밖으로 나갈 수 없는 데이터에 그대로 적용할 수 있다. 7B 모델과 CPU 환경을 기준으로 설계해 GPU 없이도 동작하며, 소규모 조직이 감당할 수 있는 하드웨어에서 실용 성능이 나온다는 점을 측정으로 보였다.

확장 방향은 세 가지다. 첫째, 도메인별 스키마 카드를 추가해 다른 업무 데이터베이스로 옮긴다. 둘째, 그래프 온톨로지를 조직도나 자산 관리 같은 관계 중심 데이터로 확대한다. 셋째, 읽기 전용 가드 위에 승인형 쓰기 도구를 계층으로 추가한다.

### 기타

**혁신성 및 차별성**

일반적인 RAG 구현은 청킹과 임베딩 설정을 조정해 정확도를 올린다. 이 프로젝트는 조정 대신 분기와 구조 보존을 택했고, 그 선택이 실제로 정확도를 좌우한다는 것을 제거 실험으로 보였다. 라우터와 융합, 큐레이션 전 구간에 LLM 호출과 튜닝 파라미터가 없어 재실행 결과가 동일하다는 점도 운영 관점의 차별점이다.

**한계점 및 향후 로드맵**

- 라우팅 30/30은 공개된 예시 문항 기준(in-sample)이다. 홀드아웃 두 벌로 일반화를 따로 쟀다 — 템플릿 문형 **0.900**, 업무 담당자 구어체 **0.633**. 관계 표현이 무한해 규칙 기반이 어휘로 따라잡을 수 없으므로 개체 타입 쌍을 온톨로지 엣지에 대조하는 방식으로 바꿨고, 그것이 천장을 늦춘 것이지 없앤 것은 아니다. 두 홀드아웃은 각각 결함 진단에 소진돼 더 이상 홀드아웃이 아니다.
- 7B 모델은 자연어 해석에서 실제 오답을 낸다. 남은 오답 3건의 원인을 그대로 공개했고, 공개된 30문항에 맞춰 프롬프트를 더 손대면 과적합이 된다고 판단해 멈췄다.
- 스키마 카드의 기여를 재검증한 결과, 실패한 SQL을 데이터베이스 카탈로그와 함께 한 번 되먹이는 재시도를 붙이면 정확도 차이가 사라지고(양쪽 7/10) 이득이 호출 수 감소로 이동했다(12회 대 16회). 자기 주장을 스스로 반증한 결과이므로 숨기지 않고 보고서에 남긴다.
- 향후: 3차 홀드아웃(오탈자·축약·복합 질문·환각 유도), 승인형 쓰기 도구, 다중 데이터베이스 라우팅, 자동 장애 조치, MCP HTTP 전송(현재는 stdio 전용이라 컨테이너가 TCP 포트를 열지 않는다).

**소감 및 후기**

가장 크게 배운 것은 측정이 주장을 이긴다는 점이다. 스키마 카드가 정확도의 핵심이라고 믿고 지표를 만들었는데, 재시도를 붙인 조건에서 그 이득이 비용 절감으로 바뀌는 것을 확인했다. 데이터셋에 없는 회사명을 물었을 때 모델이 담당자를 지어내던 순간도 마찬가지였다. 검색 지표만 보고 있었으면 놓쳤을 결함이라, 이후로는 레인 점수가 아니라 실제 답변을 기준으로 검증했다.
