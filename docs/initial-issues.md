# 공개 직후 등록할 이슈 초안

> 저장소를 공개한 시점에 이대로 등록한다. 실제 작업 이력이 이슈와 PR로 남는 것이 이 프로젝트의 관리체계 증거다.
> 형식은 `.github/ISSUE_TEMPLATE/`의 두 템플릿을 따른다. 라벨이 붙은 항목은 그 라벨로 등록한다.

## enhancement

### 1. 홀드아웃 평가셋으로 라우팅 일반화 성능 측정
`enhancement`

현재 라우팅 정확도 30/30은 사업자가 공개한 예시 문항 기준이며 라우터 어휘를 그 문항을 읽으며 작성했다. 즉 in-sample 수치다.

- 공개 30문항과 어휘가 겹치지 않는 홀드아웃 문항 30개 이상 작성
- 라우팅 라벨과 종단 근거 포함률을 홀드아웃에서 재측정
- 공개 문항 성능과 나란히 보고, 격차를 그대로 공개

관련: `docs/report.md` §0.5, `docs/roadmap.md` 1번

### 2. 다국어 공식 768차원 임베딩 후보 대조
`enhancement`

`vector(768)` 스키마를 유지하려고 bge-m3의 1024차원 출력 중 앞 768개만 저장하고 있다. 68문항 실측에서 손실은 관측되지 않았지만, 모델 카드가 보증한 출력 모드는 아니다.

- 다국어이면서 공식 768 출력을 명시하는 모델 후보 조사
- 같은 68문항으로 대조, 사전 등록 기준(nDCG@5 CI 하한 -0.03 이내) 적용
- 통과 시에만 교체하고 실패도 결과에 남긴다

참고: 영어 전용 768 모델(nomic-embed-text)은 같은 한국어 문항에서 25/68이라 대안이 아니다. `docs/report.md` §0.9

### 3. 키워드 검색 레인 추가
`enhancement`

dense 벡터만으로는 고유명사와 코드 문자열의 정확 일치 질의가 약하다. PostgreSQL 전문검색 또는 2-gram 인덱스 기반 레인을 RRF의 네 번째 소스로 추가한다.

- 한국어 형태소 분석 확장 설치 가능 여부를 배포 환경에서 먼저 확인
- 레인 추가 전후를 같은 평가셋으로 비교
- 지연 예산 초과 시 채택하지 않는다

### 4. NL2SQL 평가 문항 확장과 실패 유형 분류
`enhancement`

SQL 채점 문항이 10개뿐이라 6/10과 7/10의 차이를 통계적으로 말할 수 없다.

- 정답 SQL을 직접 작성해 문항을 40개 이상으로 확장
- 실패를 유형별로 분류(존재하지 않는 컬럼, 조인 누락, 필터 과잉, 집계 오류)
- 유형별 빈도를 보고 다음 수선 대상을 정한다

## good first issue

### 5. 라우터 어휘 사전에 동의어 추가
`good first issue` `enhancement`

`air-server/src/router.ts`의 어휘 사전은 스키마와 그래프 온톨로지에서 뽑은 단어로 이루어져 있다. 같은 뜻의 한국어 표현을 추가하면 분기 정확도가 올라갈 수 있다.

- 데이터베이스 없이 `node dist/router.test.js`로 검증된다
- 추가한 어휘가 다른 레인의 분기를 깨지 않는지 기존 테스트로 확인
- 어휘는 반드시 스키마나 온톨로지에 근거해야 한다. 평가 문항에서 뽑지 않는다

### 6. 오프라인 단위 테스트 추가
`good first issue` `test`

현재 오프라인에서 도는 테스트는 라우터, 큐레이터, RRF, 실행일치 비교기 네 개(120단언)다. 데이터베이스 없이 검증 가능한 순수 함수가 더 있다.

- `src/text.ts`, `src/candidate.ts`처럼 외부 자원이 없는 모듈이 대상
- 경계값과 잘못된 입력을 함께 다룬다
- CI에 자동으로 포함된다

### 7. 오류 메시지에 다음 행동 추가
`good first issue`

데이터베이스나 Ollama가 없을 때 나오는 오류가 원인만 알려 주고 다음에 무엇을 하면 되는지 말하지 않는 곳이 있다.
