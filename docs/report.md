## 0.5 공식 데이터셋(Company-X) 실측 — 사업자 배포본 그대로

리원에이스가 2026-07-22 공개한 **공식 데이터셋**(`companyx-dataset-v1.0.zip`, SHA-256 `30084767…0827d772`, 출처 https://liwonace.co.kr/blog/9)을 **원본 DDL 그대로** 적재하고 3개 도구 레인을 전부 실측했다. 사내 합성 벤치가 아니라 **심사자가 준 데이터** 위의 숫자다.

적재 실측 (`eval/results/companyx-load.json`): 8테이블 **818행** · 문서 40건 → **258청크**(섹션 원자 분할) · 그래프 **133노드/354엣지** · `entity_links` 133건(그래프 노드 ↔ 관계형 행 1:1 브릿지). **공식 DDL은 한 글자도 바꾸지 않았다** — 로더의 `ddlDeviations`가 빈 배열이다. 초기 구현은 `vector(768)`을 1024로 넓혔으나, §0.8의 리서치·실측 결과로 원본 폭을 지키는 쪽이 옳다고 판정해 되돌렸다.

| 레인 | 지표 | 결과 | 오라클 |
|---|---|---|---|
| **라우터** | 공식 30문항 도구 라벨 일치 | **30/30 = 100%**, 20회 재실행 바이트 동일 | 사업자가 붙인 `tool` 라벨 (외부 라벨) |
| **NL2SQL** (재시도 없음) | execution match, 큐레이션 스키마카드 | **8/10** (2026-10-01 CPU 컨테이너 정본, `qwen2.5-coder:7b`, 5회 반복 동일. 08-19 호스트 측정은 7/10, 옛 `qwen2.5:7b` 는 5/10 과 7/10 사이에서 세션마다 달랐다, §0.10) | gold SQL 실행 결과 = DB (LLM 저지 없음) |

| **end-to-end `ask`** | 답변 접지 (컨텍스트 밖 개체 생성) | **0건 / 18문항**, 3회 연속 | 답변 개체 ⊆ 컨텍스트 |
| **end-to-end `ask`** | 미존재 개체 질의 거절 | **성공** (「주어진 정보로는 알 수 없습니다」) | 서울물산 케이스 |

읽는 법 세 가지.

1. **라우터 100%는 in-sample이다.** 30문항은 사업자가 *공개한 예시*이고 라우터 어휘를 그 문항을 읽으며 작성했다. 일반화 수치가 아니라 "3레인 분기가 사업자 의도와 일치한다"는 확인으로 읽어야 한다. 어휘 자체는 스키마·그래프 스키마에서 뽑았지 라벨에서 뽑지 않았다.
2. **NL2SQL 60%의 ablation이 본 프로젝트의 논지를 사업자 데이터에서 재현한다 — 옛 `qwen2.5:7b` 에서는 재시도를 붙이면 그 논지가 무너졌지만 `qwen2.5-coder:7b` 에서는 재시도를 붙여도 격차가 남는다(§0.6).** 테이블명만 준 베이스라인의 실패 8건 중 6건이 **존재하지 않는 컬럼 환각**(`contracts.is_active`, `clients.registration_date`, `employees.department_id` …)이었다. 값 어휘(`quarter='2025-Q3'`, `status='active'`)까지 담은 스키마 카드를 주면 그 실패군이 사라진다. 내부 벤치의 Δ +51.0pp와 같은 방향이며, **같은 데이터·같은 모델·같은 채점기**로 측정했다.
3. **남은 4건은 숨기지 않는다.** ① `보안 솔루션 … 월 평균 매출` = 모델이 OR 우선순위를 틀림(진짜 오답), ② `활성 계약 수` = 스키마 카드에 `status['active'…]`가 있는데도 `is_active` 환각, ③ `평균 연봉이 가장 높은 부서` = `dept_id`만 반환(부서명 조인 누락), ④ `가장 많은 프로젝트를 진행 중인 고객사` = 모델이 `status='in_progress'` 필터를 **추가**했다 — 사업자 hint는 필터 없이 GROUP BY만 지시하므로 gold 기준으로는 오답이지만 질문 문면("진행 중인")으로는 모델 쪽이 더 충실한 해석이다. 이 4건은 7B 한계와 질문 모호성이지 파이프라인 결함이 아니다.

**그래프 레인은 이번에 새로 만들었다.** 공식 라벨이 요구하는 `knowledge_graph`가 기존 라우터에 아예 없었고(구 라우터 = structured/semantic 2레인), 초기 실측 평균 recall은 **0.278**이었다. 원인 4가지를 고쳐 **1.000**으로 올렸다: ① 확장이 out 방향뿐이라 역방향 질의("Product-C1을 **사용하는** 고객사")가 조용히 0건 반환 → 양방향 BFS, ② 시드가 substring 매칭 상위 5건이라 `Product-C1`을 물으면 엉뚱한 제품이 시드 → exact>prefix>substring 랭킹, ③ 노드를 지목하지 않고 **관계만** 지목하는 질의("가장 많은 고객을 **담당하는** 직원")는 시드가 없어 시작 불가 → 관계 단위 스캔·차수 집계 도입(집계는 DB가 하고 모델은 읽기만), ④ 노드 속성 미적재로 `status='in_progress'` 필터 불가 → 속성 적재.

**환각 방지 게이트(실측).** 사업자 예시 24번 `서울물산 담당 엔지니어는 누구야?`의 **서울물산은 데이터셋에 존재하지 않는다**(고객사는 `Client-A…Client-AD`, questions.json에만 등장). 이때 관계 전체(MANAGES_ACCOUNT 63엣지)를 컨텍스트로 밀어 넣으면 7B는 그럴듯한 담당자를 **지어낸다**. 그래서 "질의가 개체를 지목했는데 온톨로지에서 해소 실패 + 관계 단위 의도 없음" 조건에서 컨텍스트를 **0엣지 + 명시적 not-found 한 줄**로 만든다(`eval/results/companyx-kg.json → unresolved_gate_fired: 1`). 데이터셋 결함은 사업자에게 별도 문의했다. 게이트는 못 찾은 이유도 `not_found` 로 낸다 — 비슷한 이름도 없으면 `not_in_database`, 이름이 비슷한 다른 개체(`클라우드사업팀` → `클라우드사업부`)만 있으면 `similar_name_mismatch` 이고 그 개체는 후보로만 알린다. 이때 `ask` 는 7B 를 부르지 않고 사유 문장으로 답한다(2026-09-30 실측: 「질문에 나온 개체(서울물산)를 데이터베이스에서 찾지 못했습니다. 이름이 비슷한 개체도 없습니다. 해당 개체는 데이터셋에 존재하지 않습니다.」). 위 표의 「주어진 정보로는 알 수 없습니다」는 이 변경 전 실행의 7B 답이다.

## 0.6 자기 반증, 그리고 그 반증이 다시 뒤집힌 것 — 스키마 카드의 기여는 모델에 의존했다

> **2026-08-19 갱신 — 이 절의 결론은 뒤집혔다.** 생성 모델을 `qwen2.5:7b` 에서 `qwen2.5-coder:7b` 로 바꾸고 같은 실험을 다시 돌리니 **차이가 사라지지 않는다**: 재시도를 붙여도 **7/10 대 5/10** 이고 수리 횟수는 **0회 대 7회** 다(2026-10-01 CPU 컨테이너 정본은 8/10 대 5/10, 0회 대 8회). 스키마 카드를 주면 이 모델은 **수리가 아예 필요 없다.** 아래 서술과 표는 `qwen2.5:7b` 에서 관측한 그대로 남긴다 — **지우지 않는다.** 자기 반증을 한 번 했고 그 반증이 다시 뒤집혔으며, 두 번 다 우리가 재서 알았다. **결론이 모델에 의존한다는 것을 실측으로 보인 사례**로 읽어 주기 바란다.

실패한 SQL을 **데이터베이스 자신의 카탈로그**(information_schema 실컬럼 목록)와 함께 모델에 한 번 되먹이는 self-repair를 붙이자, `qwen2.5:7b` 에서는 스키마 카드 유무의 **정확도 차이가 사라졌다**.

| 조건 | 정확도 | LLM 호출 | 총 소요 | 재시도 |
|---|---|---|---|---|
| 스키마 카드, 재시도 없음 | 60% | 10회 | — | — |
| 테이블명만, 재시도 없음 | 20% | 10회 | — | — |
| 스키마 카드 + 재시도 1회 | **70%** | **12회** | **8.7초** | 2건 |
| 테이블명만 + 재시도 1회 | **70%** | 16회 | 11.6초 | 6건 |

**해석을 바꿔야 한다.** 스키마 카드와 self-repair는 다른 기능이 아니라 **같은 병(모델이 스키마를 모른다)의 사전 처방과 사후 처방**이다. 사전에 주면 첫 호출에 맞고, 사후에 고치면 두 번째 호출에서 맞는다. 그래서 재시도가 있는 시스템에서 스키마 카드가 사는 근거는 정확도가 아니라 **호출 수 33% 감소, 지연 25% 감소, 실패 경로 3분의 1**이다. 재시도가 없는 경로에서는 Δ +40pp의 정확도 차이가 그대로 남는다(이 문단의 수치는 전부 `qwen2.5:7b` 에서 잰 것이다).

이 결과는 내부 벤치의 「구조보존 큐레이션 Δ +51.0pp」를 **부정하지 않지만 조건을 붙인다**: 그 수치는 재시도 없는 단발 호출 조건의 값이다. 사업자 데이터도 같은 조건에서 같은 방향을 냈다 — 다만 **두 수의 모델이 다르다.** 위 표의 Δ +40pp(60% 대 20%)는 `qwen2.5:7b` 에서 잰 것이고, 정본 Δ +51.0pp는 현행 `qwen2.5-coder:7b` 값이다. 현행 모델로 같은 사업자 데이터를 재시도 없이 재면 8/10 대 1/10, 즉 **Δ +70pp**다(2026-10-01 정본). 세 수를 한 줄에 세워 「재현」이라 부르면 모델을 넘나든 비교가 되므로, 각 수의 모델을 붙여 읽어야 한다. 그리고 재시도를 허용하면 이득이 정확도에서 비용으로 이동한다 — **이것도 구 모델에서의 관측이고**, 현행 모델은 재시도를 붙여도 8/10 대 5/10으로 격차가 남는다(위 갱신 상자).

self-repair 자체는 튜닝 파라미터를 늘리지 않는다. 재시도 조건은 "엔진이 오류를 냈는가" 하나뿐이고, 성공한 쿼리는 재시도되지 않으며, 임계값도 샘플링도 없다.

## 0.7 제품 경로(`ask`) 실측 — 레인 점수가 아니라 실제 답변

레인 평가는 **검색**을 재고 심사자가 보는 것은 **답변**이다. 30문항 전부를 `ask`(route → 병렬 fan-out → RRF → 큐레이션 → 온프렘 7B)로 돌려 LLM 저지 없이 셋을 측정했다. ① 큐레이션된 컨텍스트가 정답 근거를 담았는가 ② 답변이 언급한 데이터셋 개체가 전부 컨텍스트 안에 있는가(밖이면 지어낸 것) ③ 미존재 개체 질의를 거절하는가.

**첫 실행에서 결함 5개가 드러났고 전부 "검색은 맞는데 출력이 새는" 유형이었다.** 레인 평가만 봤으면 못 봤을 것들이다.

| 증상 | 진단 | 수정 |
|---|---|---|

## 0.8 사업자 공개자료 정밀독해 — 물어보는 대신 읽고 재는 쪽을 골랐다

담당자 메일을 받고 문의 5건을 정리했으나, 보내기 전에 사업자가 이미 공개한 것을 전부 읽었다. 블로그 9편·제품 19종·서비스 7종·공지 3건(**99페이지**), **air 공식 문서 34페이지(196KB)**, 그리고 과제가 「필수 참조」로 지정한 **논문 2편 PDF 전문**이다. 결과적으로 **5건 중 4건이 닫혔고 출제자만 답할 수 있는 1건만 남았다**.

### 0.8.1 필수 참조를 인용에서 근거로

**전현우·김태성·강현 2026** (zenodo 18842478, 저자 소속에 **Liwonace Corp.** 포함): 컨텍스트 4성분 K·A·D·G의 2⁴ 요인실험 3,805런. ① 풀 컨텍스트가 빈 baseline 대비 유의(Qwen **d=0.835, p<0.001**) ② **K(지식베이스)만 유의한 주효과**(Δ=0.119, p=0.028) ③ K+A vs Full에서 **Qwen만 풀 컨텍스트가 유의하게 우수**(p<0.001, d=-0.347), Llama는 차이 없음.

→ 본 구현이 Qwen2.5-Coder-7B를 쓰고 큐레이션된 컨텍스트를 공격적으로 트림하지 않는 것은 이제 취향이 아니라 **이 실측치**에 근거한다. 그리고 「K만 유의」는 컨텍스트 예산 배분의 지침이 된다 — §0.7에서 그래프 레인의 이름매칭 줄(부기성 정보)을 엣지(K) 뒤로 미룬 수정이 이 방향과 일치한다.

**Pylon-7** (zenodo 18808598): 615런, CPU-only 보급형 하드웨어. ① 계층화가 **토큰 47%↓·정확도 37%↑ 동시 달성** ② **L3가 sweet spot**, 과도한 제약(L4)은 정확도 소폭 하락 ③ **7B+MCP가 20B 단독보다 3.5배 저렴·14.4%p 정확**. 설계 원칙은 Descent Cost(하위 계층일수록 비용·위험 증가)·Gateway·Independence.

### 0.8.2 그 독해가 잡아낸 우리 결함 두 가지

**(1) Pylon-7 계층 번호를 거꾸로 붙이고 있었다.** 논문 Table 1은 **L7 Interface(위험 최소) → L1 System(셸·root, 위험 최대)**의 내림차순이다. 본 구현은 `route:2 / graph:5 / retrieve:4`였는데 논문 기준으로는 각각 **L5 Routing / L3 Resource / L6 Analysis**다. 특히 route에 붙였던 2번은 논문에서 **L2 = Mutation(코드 수정, High risk)** 자리다. 필수 참조를 인용하면서 그 표를 반대로 쓰고 있었다.

**(2) air Meter의 L1~L7은 Pylon-7과 방향이 반대다.** air 공식 문서(`guide/meter`)의 Meter는 **비용 오름차순**(L1 정적응답 → L2 조회 → L6 LLM 호출 → L7 에이전트 체인)이고, `defineTool`의 `layer`는 **Meter의 자동 분류를 오버라이드한다**. 거기에 Pylon-7 번호를 넣으면 비용·지연 통계가 통째로 잘못된 계층에 집계된다.

→ 그래서 **`layer`는 air Meter 규약**을 따르고, **Pylon-7 위치는 `tags: ["pylon7:Lx"]`**로 분리했다. 두 체계를 다 읽지 않으면 보이지 않는 충돌이다.

→ 정리하고 나니 드러난 사실 하나: 7개 도구 중 **Pylon-7 L2(Mutation)·L1(System)에 해당하는 도구가 하나도 없다.** 전 도구가 읽기 전용이고 `sql.query`는 NOLOGIN `mcp_ro`로 강등된다. Descent Cost Principle 관점에서 **비용·위험이 최대인 두 계층에 애초에 내려가지 않는 설계**다.

### 0.8.3 임베딩 차원 — 물어볼 문항을 실측으로 대체했다

사업자 입장은 세 곳에서 일관된다. 공지는 "**Ollama의 임베딩 모델을 활용하여 적재**"라고만 하고 모델을 지정하지 않는다. 블로그(VectorDB 튜닝)는 "**PCA나 Matryoshka로 768 또는 512차원으로 줄여도 검색 품질 차이는 미미**"라고 쓴다. 자사 제품 Bubble Embedding은 **512차원·CPU only·한국어 특화**다. 반면 같은 블로그(RAG 실수 5가지)는 "**범용 영어 임베딩을 그대로 쓰는 것은 실수, 한국어 문서는 도메인 특화가 훨씬 정확**"이라고 못 박는다.

즉 요구는 「차원은 작게, 단 한국어를 포기하지 말 것」이다. 그러면 768 네이티브 영어 모델로 갈아타는 것은 오답이고 한국어 모델을 잘라 쓰는 것이 정답이다. 사업자 코퍼스에서 직접 쟀다.

| 임베더 | dim | hit@5 | 문서 타입 정밀도 |
|---|---|---|---|
| hash (오프라인 결정론) | 1024 | 0.75 | 1.000 |
| BGE-M3 | 1024 | **1.00** | 0.971 |
| **BGE-M3 → 768 절단+재정규화 (채택)** | **768** | **1.00** | 0.943 |
| BGE-M3 → 512 절단+재정규화 | 512 | **1.00** | 0.971 |
| nomic-embed-text (768 네이티브) | 768 | 0.75 | **0.486** |

**결론: 공식 `vector(768)`을 원본 그대로 쓴다.** nomic으로 갈아탔다면 타입 정밀도가 0.971 → 0.486으로 반토막 났을 것이다. 귀사 블로그의 처방을 귀사 데이터에서 검증한 결과이며, 이로써 스키마 변경 사유가 사라졌다(`ddlDeviations: []`).

### 0.8.4 air를 3/19에서 8개로, transport는 설정 한 줄로

air는 **19개 플러그인**을 제공하는데 본 구현은 timeout/retry/circuitBreaker 3개만 쓰고 있었다. 이 워크로드가 **전 도구 읽기 전용 + 결정론**이라는 성질에 근거해 5개를 더했다.

`jsonLogger`(ELK/Datadog 호환 감사 로그) · `sanitizer`(도구 입력은 외부 입력이다, Hou 2025 위협모델) · `queue`(온프렘 7B 경로만 동시 2로 좁힘) · `dedup`(병렬 fan-out의 동일 하위호출 제거) · `cache`(**결정론이 캐시를 안전하게 만든다** — 같은 질의가 같은 결과를 보장하므로 TTL 캐싱이 정확도를 훼손하지 않는다).

쓰지 않은 것에도 근거를 둔다: auth/cors/rateLimit은 stdio 로컬 배포에 불필요하고, transform/i18n은 응답 계약을 흐리며, dryrun은 개발 전용이다.

또한 이전 문서가 "stdio→HTTP transport는 후속"이라고 적어둔 항목은 **air가 설정 한 줄로 지원**한다(`transport: { type: 'sse', port }`). `MCP_TRANSPORT=sse`로 전환된다. 다만 **소스에 분기가 있다는 것과 그 분기가 도는 것은 다르다** — stdio 는 데모가 매번 종단으로 밟지만 sse 는 띄워본 기록이 없었다. `scripts/verify-sse-transport.mjs` 로 initialize → tools/list 까지 실행해 도구 8종 열거를 확인했다(2026-08-17).

### 0.8.5 남은 최대 갭 — 키워드 검색

사업자 Vector Engine 제품 페이지는 "**벡터 검색만으로는 부족합니다. 키워드 검색과 결합해야 정확합니다**"라고 명시하고, 시맨틱 + BM25를 **RRF**로 융합한다. 본 구현은 RRF를 쓰지만 융합 대상이 SQL·벡터·그래프이고 **키워드 검색 레인이 없다**. PostgreSQL FTS(tsvector) + 한국어 바이그램은 추가 의존성 없이 구현 가능하며 RRF의 네 번째 소스로 들어간다. 이것이 다음 작업 1순위다.


## 0.9 벡터 레인 재평가 — 8문항을 68문항으로 늘리고, 우리가 자른 차원을 직접 쟀다

**왜 다시 쟀나.** 기존 벡터 평가는 채점 가능한 문항이 8개였다. hit@5 = 1.00처럼 보였지만 그 표본에서 정확도 1.0의 95% Wilson 하한은 0.676이다. 즉 "임베딩 모델이 좋다"도 "차원을 잘라도 괜찮다"도 이 수치로는 말할 수 없었다. 그리고 R4 리서치에서 **bge-m3 모델 카드가 dense 1024만 명시하고 Matryoshka 축소를 주장하지 않는다**는 것이 확인되면서, 우리가 앞 768개만 저장해 온 방식이 공식 출력 모드가 아니라는 사실이 드러났다.

**어떻게 늘렸나.** `eval/companyx/build_vector_gold.py`가 71문항을 만든다(채점 가능 68). 오라클 계약은 그대로다 — 문서가 정답인 조건은 `keywords`를 전부 포함하는 것이고 검색기는 질문 문장만 본다. 생성기가 강제하는 것은 셋이다. ① 정답 집합 크기 1~3(0이면 채점 불가, 4 이상이면 변별력 없음) ② 문서 40건 전부 커버 ③ `style` 표기 — `paraphrase` 30문항은 **키워드를 질문에 한 글자도 노출하지 않는다.** 어휘가 겹치면 의미 검색이 아니라 문자열 매칭을 재게 되기 때문이다.

| BGE-M3 원본 | 1024 | **67/68 = 0.985** | [0.921, 0.997] | 37/38 | **30/30** | 0.891 | <!--metric-ok-->

**읽는 법 네 가지.**

1. **절단의 손실이 관측되지 않았다.** 1024와 768은 총점이 같고, 서로 다른 문항 하나씩을 놓쳤다(불일치 쌍 1대 1, McNemar exact p = 1.0). 이 코퍼스, 이 표본에서 우리 절단은 성능을 깎지 않았다. 다만 **"공식 지원 모드가 아니다"는 사실은 측정으로 바뀌지 않는다.** 그래서 보고서와 README는 이를 기능이 아니라 제약으로 적는다.
2. **"공식 768 모델로 바꾸면 된다"는 단순 처방은 반증됐다.** 우리가 로컬에서 확보한 공식 768 출력 모델(nomic-embed-text)은 영어 전용이고, 같은 한국어 문항에서 25/68에 그쳤다. paraphrase 문항에서는 6/30으로 무너진다. 차원의 공식성보다 **언어 적합성이 먼저**라는 것이 이번 실측의 결론이다. 다국어이면서 공식 768을 내는 모델이 확보되면 그때 다시 대조한다.
3. **해시 폴백은 폴백이다.** 53/68로 실사용 품질이 아니며, paraphrase에서 25/30으로 버티는 것은 이 코퍼스의 어휘 반복 때문이다. CI에서 임베딩 모델 없이 파이프라인이 도는지 확인하는 용도 이상으로 쓰지 않는다.
4. **표본은 늘었지만 코퍼스는 그대로다.** 문서 40건이라 절대 성능을 일반화할 수 없다. 이 표는 모델 간 상대 비교이지 제품 성능 보증이 아니다.

**재현.**

```bash
python eval/companyx/build_vector_gold.py            # 평가셋 생성·검증(문항 71, 채점 68, 커버리지 40/40)
node scripts/pg-keepalive.mjs &                      # WSL2 PostgreSQL 유휴 종료 방지
cd air-server
CX_COMPARE=1 CX_TOPK=5 CX_MODELS="bge-m3,nomic-embed-text,bge-m3@768" node dist/cli/companyx-vector-eval.js
```

> 환경 주의: 이 개발 환경의 PostgreSQL은 WSL2 안에서 돈다. WSL VM이 유휴 상태로 60초쯤 지나면 배포판이 내려가면서 PostgreSQL이 fast shutdown되고, 진행 중이던 평가 세션은 `57P01`로 끊긴다(2026-07-29 실측, WSL 로그에서 `received fast shutdown request` 확인). 임베딩 백필처럼 DB를 몇 분 놀리는 작업은 배포판을 붙잡아 두고 돌려야 한다.

## 0.10 NL2SQL 2x2 재측정 — 인용하던 수치의 근거가 없었고, 한 번 재서 쓰면 안 되는 수치였다

**어떻게 드러났나.** 2026-07-29 심사 시뮬레이션 레인이 "저장소의 `companyx-sql-llm.json`은 8/10인데 문서는 6/10이라고 적혀 있다"고 지적했다. 확인해 보니 재시도를 켠 실행이 같은 파일 경로에 덮어써 있었고, **문서가 헤드라인으로 인용하던 재시도 없는 수치의 원자료가 저장소에 남아 있지 않았다.** 평가 CLI가 조건과 무관하게 전략별로 한 파일에만 쓰고 있었다.

**첫 번째 수선.** `companyx-sql-eval.ts`가 `CX_REPAIR=0`일 때 `-norepair` 접미사로 별도 파일에 쓰도록 바꿨다. 2x2 네 칸이 동시에 남는다.

**그런데 재측정 과정에서 더 큰 문제가 나왔다.** 같은 코드, 같은 조건(스키마 카드, 재시도 없음)으로 돌린 결과가 세션에 따라 7/10과 5/10으로 갈렸다. 그래서 반복 실행기(`companyx-sql-repeat.ts`)를 만들어 조건별로 3~5회씩, 총 16회를 돌렸다.

| 조건 | `qwen2.5-coder:7b` (2026-08-19, 5회 반복) | `qwen2.5:7b` (2026-07-29) | 당시 채택 표기 |
|---|---|---|---|
| 스키마 카드, 재시도 없음 | **7/10** (5회 전부 동일) | 5/10 | 당시 **5~7/10** |
| 테이블명만, 재시도 없음 | **1/10** (5회 전부 동일) | 1/10 | **1/10** |
| 스키마 카드, 재시도 1회 | **7/10** (5회 전부 동일, 재시도 **0회**) | 7~8/10 (재시도 2회) | 당시 **7~8/10** |
| 테이블명만, 재시도 1회 | **5/10** (5회 전부 동일, 재시도 7회) | 5/10 | **5/10** |

**세션 안에서는 완전히 결정적이고, 세션이 바뀌면 1~2문항이 움직인다.** temperature 0과 seed를 고정했는데도 그렇다. 원인은 모델 재적재나 런타임 배치 상태로 추정하지만 이 라운드에서 확인하지 못했으므로 `미확인`으로 둔다. 확실한 것은 **단일 실행 수치를 헤드라인으로 쓰면 그 자체가 과장**이라는 점이다. 그래서 이 보고서의 NL2SQL 수치는 전부 범위로 적는다.

**해석.**

- 재시도가 없을 때의 격차는 **Δ +60pp**(7/10 대 1/10)로 여전히 크다. 스키마 카드 없는 팔은 `qwen2.5-coder:7b` 5회 반복에서 예외 없이 1/10이었고, 옛 `qwen2.5:7b` 에서는 8회 반복에서 예외 없이 2/10이었다.
- **`qwen2.5:7b` 에서는** 재시도를 붙이면 격차가 **0~+10pp**로 사라지거나 한 문항 수준으로 줄어든다. 이 세션(2026-07-29)에서는 두 팔이 7/10으로 **정확히 같았다**. §0.6의 당시 결론이 다시 재현된 셈이다. **2026-08-19 에 생성 모델을 `qwen2.5-coder:7b` 로 바꾸고 다시 재니 이 결론은 더 이상 성립하지 않는다** — 재시도를 붙여도 7/10 대 5/10 으로 격차가 남는다(§0.6).
- 남는 차이는 비용이다 — **`qwen2.5:7b` 기준.** 같은 7/10을 스키마 카드는 **재시도 2회**로, 테이블명만은 **재시도 6회**로 달성한다. `qwen2.5-coder:7b` 에서는 애초에 같은 점수에 도달하지 못하고(7/10 대 5/10) 재시도는 **0회 대 7회**다.

**항상 틀리는 세 문항(재시도 조건 기준).**

| 문항 | 질문 | 우리 SQL | 판정 |
|---|---|---|---|
| CX-SQL-03 | 보안 솔루션 카테고리 제품들의 월 평균 매출 | 제품별로 GROUP BY 해서 제품 수만큼 행을 반환 | 사업자 hint는 카테고리 전체의 단일 평균이다. 질문의 "제품들의"를 제품별로 읽은 해석 차이이며 모델 오답으로 계상한다 |
| CX-SQL-06 | 가장 많은 프로젝트를 진행 중인 고객사 | `status='in_progress'` 필터를 추가 | 사업자 hint에는 필터가 없다. gold 기준으로는 오답이지만 질문 문면으로는 모델 쪽이 더 충실하다 |
| CX-SQL-07 | Critical 우선순위 중 아직 해결되지 않은 건 | `status != 'resolved'` | hint는 `IN ('open','in_progress')`. `!=`는 `closed`까지 포함하므로 진짜 오답 |

**시도했다가 되돌린 처방.** CX-SQL-07을 겨냥해 "부정 조건에는 `!=` 대신 값을 `IN`으로 나열하라"는 열거형 규칙을 프롬프트에 넣어 봤다. 데이터셋과 무관한 일반 규칙이라 과적합은 아니라고 판단했는데, **재실행 결과 모델은 같은 SQL을 그대로 냈고 점수도 변하지 않았다.** 효과 없는 문장을 남기면 "튜닝 파라미터 0"이라는 주장만 흐려지므로 되돌렸다. 코드에는 되돌린 이유를 주석으로 남겼다.

**교훈 둘.** 하나, 평가 조건이 여러 개인데 출력 파일이 하나면 마지막 실행만 살아남고 문서는 사라진 근거를 계속 인용한다. 둘, 로컬 소형 모델의 수치는 한 번 재서 쓰면 안 된다. 반복 실행기와 조건별 원자료를 저장소에 남긴 이유다(`eval/results/companyx-sql-repeat-*.json`).

## 0.11 키워드(희소) 레인 — 만들고, 재고, 기본값에서 껐다

**왜 만들었나.** 2026년 검색 구성의 표준은 밀집과 희소를 함께 쓰는 것이다. 밀집 임베딩은 의미가 가까운 것을 잘 찾지만 `Product-C1`과 `Product-C2`처럼 **글자가 정확히 맞아야 하는** 질의에서 약하다. 우리는 밀집만 쓰고 있었고, 그것이 확인된 결손이었다.

**어떻게 만들었나.** PostgreSQL의 한국어 형태소 분석은 확장 설치와 superuser 권한을 요구해서 심사자의 재현 환경을 무겁게 만든다. 그래서 다른 길을 택했다. **정규화 계약을 앱에 정의하고(`air-server/src/normalize.ts`) 그 결과를 `simple` 설정의 tsvector에 넣는다.** 색인과 질의가 같은 함수를 통과하므로 계약이 코드로 남고 테스트로 검증된다.

계약이 다루는 것: 조사와 어미(고객사가 → 고객사), 띄어쓰기 변형(고객 사 → 고객사), 혼용 표기(Product-C1 → product, c1, productc1), 스키마 어휘 동의어(클라이언트 → 고객사, 진행중 → in_progress), NFKC와 소문자. 동의어 사전은 **스키마와 그래프 온톨로지에 실재하는 어휘로만** 만들었다. 평가 문항에서 뽑으면 그건 과적합이다.

**결과 (68문항, 같은 코퍼스, `eval/results/companyx-hybrid.json`).**

> 이 표의 수치는 **68문항 평가셋 시점**의 측정이다. 이후 사업자 문항 3건을 gold에 되살려 74문항이 됐고 현행 hit@5는 0.986이다. 판정(융합 기각)은 순위 품질 비교라 표본이 바뀌어도 방향이 유지되므로 그대로 둔다. 표본이 다르다는 사실만 명시한다.

| 구성 | hit@5 | hit@1 | MRR | entity 38 | paraphrase 30 |
|---|---|---|---|---|---|
| 밀집만 (현행) | **0.985** | **0.868** | **0.913** | 37/38 | 30/30 | <!--metric-ok-->
| 키워드만 | 0.838 | 0.618 | 0.705 | 29/38 | 28/30 |
| 무조건 융합 | 0.985 | 0.706 | 0.830 | 37/38 | 30/30 | <!--metric-ok-->
| 규칙 게이트 융합 | 0.985 | 0.838 | 0.894 | 37/38 | 30/30 | <!--metric-ok-->

**판정: 기각.** hit@5는 셋 다 같지만 그건 문서가 40건인데 슬롯이 5개라 천장에 붙었기 때문이다. 순위 품질을 보는 hit@1과 MRR에서 **융합이 밀집을 떨어뜨렸다.** 무조건 융합은 hit@1을 0.868에서 0.706으로 내렸고, 식별자 조건으로 게이트를 걸어도 0.838로 여전히 아래였다. 순위가 오른 문항 6개, 내린 문항 16개다.

원인은 분명하다. 약한 레인을 같은 가중치로 섞으면 강한 레인의 상위 순위를 밀어낸다. 가중치를 조정하면 개선되겠지만 **그것은 튜닝 파라미터를 하나 만드는 일**이고, 이 프로젝트가 "라우터와 융합과 큐레이션 전 구간에 튜닝 파라미터가 없다"고 주장해 온 근거와 정면으로 충돌한다.

**그래서 코드는 남기고 기본값만 껐다.** `KEYWORD_LANE=1`로 켤 수 있고, 색인 생성기(`node dist/cli/keyword-index.js`)와 평가 하네스(`companyx-hybrid-eval.ts`)도 저장소에 있다. 문서가 40건뿐인 이 코퍼스의 결과이지 희소 검색 일반의 결과가 아니다. 식별자가 지배적이거나 문서 수가 훨씬 큰 환경에서는 달라질 수 있고, 그때 다시 재면 된다.

**남긴 것.** 정규화 계약(`normalize.ts`, 28단언)은 키워드 레인과 독립적으로 유효하다. 조사와 띄어쓰기와 혼용 표기를 한 곳에서 정의하고 검증하는 코드는 그래프 시드 매칭과 라우터 어휘에도 쓸 수 있다. 그리고 이 절 자체가 **측정하고 기각한 기록**이다. 만든 것을 전부 켜서 내보내는 것보다 이쪽이 정직하다.

## 0.12 감사 가능성 — 호출마다 무엇을 근거로 무엇을 판단했는지

**왜 만들었나.** 이 서버는 답만 내놓지 않는다. 어떤 레인을 쓸지 고르고, SQL을 거부하고, 개체를 해소하지 못하면 컨텍스트를 비운다. 그 판단들이 지금까지는 로그로만 흘러갔다. 제3자가 "왜 이 답이 나왔고 무엇이 거부됐는가"를 확인하려면 코드를 읽어야 했다는 뜻이다. 공개된 데이터베이스 MCP 서버들을 살펴봐도 호출마다 근거와 정책 판정을 하나로 묶어 내보내는 사례를 찾지 못했다.

**무엇을 만들었나.** `air-server/src/auditrecord.ts`는 파이프라인 결과를 감사 레코드로 바꾸는 **순수 변환**이다. 아무것도 실행하지 않는다.

| 절 | 담는 것 |
|---|---|
| routing | 선택된 레인, 호출 도구, 근거가 된 어휘, 결정론 여부 |
| retrieval | 레인별 실행 결과와 후보 수, SQL 원문과 거부 사유 |
| fusion | RRF 상위 항목과 **어느 소스들이 합의했는지** |
| context | 큐레이션 결과. `broken_rows`는 큐레이터 계약상 항상 0 |
| policies | **실제로 발동한 정책만.** 없는 정책을 지어내지 않는다 |
| grounding | 답변이 컨텍스트 밖 개체를 만들었는지 |

정책은 여섯 가지이고 각각 코드가 실제로 강제하는 것과 1:1 대응한다: `sql-read-only`, `sql-repair`, `sql-trust-gate`, `graph-unresolved-gate`, `context-budget`, `branch-isolation`. 판정은 allow / deny / repair / degrade이고 **deny에는 반드시 사유가 붙는다.** 사유 없는 거부 기록은 감사에 쓸모가 없다.

노출 경로는 셋이다. MCP 도구 `audit.explain`(json 또는 사람이 읽는 text), 리소스 `audit://schema/v1`(레코드 구조와 정책 의미), 그리고 `ask` 응답에 함께 실리는 레코드.

**지문을 둘로 나눈 이유.** 처음에는 지문 하나로 "결정론"을 주장했는데, 30문항을 두 번 돌려 보니 한 문항에서 값이 달랐다. 원인은 모델이 만든 SQL 문자열이 지문에 들어가 있었기 때문이다. 그래서 나눴다.

- `routing_fingerprint` — 라우팅 결정과 발동한 정책 종류만 덮는다. 모델 출력이 섞이지 않는다.
- `pipeline_fingerprint` — 모델이 만든 SQL과 융합 결과까지 덮는다.

**실측 (사업자 공개 30문항, `eval/results/companyx-audit.json`).**

| 항목 | 결과 |
|---|---|
| 정책 발동 | `context-budget:degrade` 17회, `sql-read-only:allow` 10회, `sql-repair:repair` 2회, `graph-unresolved-gate:deny` 1회 |
| 접지 위반 | **0건** (답변이 컨텍스트 밖 개체를 만든 적 없음) |
| 구조 보존 위반 | **0건** (`broken_rows` = 0, 큐레이터 계약 유지) |
| 규칙 지문 안정성 | **5/5** — 같은 질의를 두 번 돌려 라우팅과 정책이 완전히 같았다 |
| 파이프라인 지문 안정성 | **모델에 따라 다르다.** `qwen2.5:7b` 는 실행마다 흔들렸고(2026-08-18 세 번 관측: 4/5 · 3/5 · 5/5), `qwen2.5-coder:7b` 는 **세 번 다 5/5** 였다(2026-08-19). **세 번 같았다는 것은 세 번 같았다는 뜻이지 「항상」이 아니다** — 생성 모델이 끼는 경로라 원리적으로 보장이 아니다. 이 줄은 여전히 **관측**이며, 저장된 증거 파일은 마지막 실행값을 담는다 <!--metric-ok--> |

`graph-unresolved-gate:deny`가 발동한 한 건은 24번 문항(데이터셋에 없는 회사명)이다. 게이트가 의도대로 작동해 컨텍스트를 0건으로 만들었고 모델은 담당자를 지어내지 않았다.

**이 결과가 말하는 것.** "이 시스템은 결정론적이다"는 주장은 이제 범위가 정확하다. **라우팅과 정책 판정은 결정론이고, 모델이 문자열을 만드는 구간은 아니다.** 지문 하나로 뭉뚱그렸으면 그 숫자가 "가끔 비결정적"으로 읽혔을 것이다. **그래서 파이프라인 쪽은 고정 수치로 적지 않는다** — 다시 돌리면 달라지는 값을 표에 박아 두면, 심사자가 직접 돌려 다른 수를 본 순간 나머지 수치의 신뢰까지 깎인다. 나누고 나니 무엇이 보장되고 무엇이 보장되지 않는지가 그대로 드러난다.

## 0.13 평가 현대화 — 다단계 완료율과 claim 단위 접지

**왜 바꿨나.** 지금까지의 지표는 레인을 따로 봤다. SQL 5~7/10, KG 1.000, 벡터 0.986. 그런데 업계 평가는 단일 지표가 아니라 **다단계 작업 완료**를 보고, 근거 기반 생성은 **claim 단위 접지와 완전성**을 나눠서 잰다. 레인이 따로 잘돼도 연결이 안 되면 질문은 못 푼다.

**다단계 완료율.** 라우터는 한 질의를 한 레인에 맡긴다. 그래서 "Client-A가 쓰는 제품의 총 매출은?"처럼 **개체 해소 -> 관계 탐색 -> 집계를 연달아** 거쳐야 하는 질의를 한 번의 호출로는 못 푼다. v1은 단일 호출의 감사 레코드로 단계를 "정의"했는데, 그건 다단계가 아니라 한 호출에 이름표를 붙인 것이라 전부 실패했다. 그 실패가 이 절의 출발점이다.

`multistep.ts`의 `runMultiStep`이 계획을 실행한다. 각 단계는 개체 해소, 관계 탐색, 집계 중 하나이고 각각 독립 판정된다. placeholder SQL은 **이전 단계의 출력으로 조립**한다. 이것이 다단계의 본질이다.

| 작업 | 단계 | 결과 |
|---|---|---|
| Client-A가 사용 중인 제품 목록 | 해소 -> 관계 | **PASS** (3개 제품) |
| Client-A 제품들의 총 매출 | 해소 -> 관계 -> 집계 | **PASS** (매출 값 반환) |
| Product-C1 사용 고객사 평균 계약 금액 | 해소 -> 관계 -> 집계 | **PASS** (평균 값 반환) |
| Client-A 제품 월 매출 평균 | 해소 -> 관계 -> 집계 | **PASS** |
| Client-A 제품 카테고리 매출 | 해소 -> 관계 -> 집계 | **PASS** |
| 서울물산 담당 엔지니어 부서 | 해소 | **FAIL (정답)** — 데이터셋에 없는 개처이므로 개체 해소가 실패하는 것이 맞다(환각 차단) |

완료율 **5/6 = 0.833**, 단계 통과 14/15. 실패한 한 건은 존재하지 않는 개체를 가려내는 음성 사례라 완료율에 넣지 않고 별도로 기록한다.

**이 과정에서 드러난 설계 문제 하나.** 처음에는 사실 테이블(`sales`)을 이름 컬럼으로 집계했는데, 사실 테이블은 FK만 갖고 이름이 없다. 그래서 집계가 0행으로 "성공"했다. 이름을 풀려면 차원 테이블과 JOIN해야 한다. 0행 집계가 성공처럼 보이는 함정을 `detail`에 "(조건에 맞는 데이터 없음)"으로 명시하게 고쳤다.

**claim 단위 접지.** 기존 접지 검사는 "답변이 언급한 개체가 컨텍스트에 있는가"였다. 문장 전체가 지어낸 것이어도 개체 하나만 맞으면 통과다. `claims.ts`는 답변을 문장으로 나누고 각 문장에서 **검증 가능한 원자**(식별자, 수치, 날짜, 인명+직함, 상태 값)만 뽑아 컨텍스트에 있는지 잰다. LLM 심판이 아니라 문자열 일치라 채점이 결정론이다.

| 지표 | 의미 | 기존 검사와의 차이 |
|---|---|---|
| claim 접지율 | 모든 원자가 접지된 문장의 비율 | 문장 단위라 지어낸 문장이 걸린다 |
| 원자 접지율 | 접지된 원자의 비율 | 부분 실패도 본다 |
| 완전성 | 필요한 근거를 컨텍스트가 모두 덮었는가 | **방향이 반대다** — 접지는 지어내지 않음, 완전성은 빠뜨리지 않음 |

완전성을 따로 두는 이유: 아무 말도 안 하는 답변은 접지 만점이 된다. 둘을 한 지표로 뭉치면 그 함정을 못 본다.

**그 함정이 실제로 작동한 기록, 그리고 그보다 나쁜 것 (2026-08-19).** 모델을 바꾸며
답변 30건을 나란히 놓고 비교하다 한 자리를 파고들었다.

| | 질문: 「Product-D1 제품과 관련된 **프로젝트**는?」 |
|---|---|
| 조건 | 같은 컨텍스트 1,174자 · 같은 레인 `graph` · 같은 후보(graph 140 / fused 42) |
| `qwen2.5:7b` | 「Client-Y, Client-AB, Client-B, …」 — 고객사 11개를 나열 |
| `qwen2.5-coder:7b` | 「주어진 정보로는 알 수 없습니다.」 |

**세 가지가 동시에 참이다.**

1. **답은 그래프에 있다.** 관련 프로젝트는 2홉(`Product-D1` ← `USES` ← client →
   `HAS_PROJECT` → project)이고 SQL 로 세면 **15개**가 닿는다.
   `graphExpand(depth 2)` 도 **`HAS_PROJECT` 엣지 16개를 실제로 낸다.**
2. **큐레이션이 그것을 버린다.** 최종 컨텍스트 1,174자에 `HAS_PROJECT` 가 **0건**이다 —
   1홉 `USES` 엣지가 예산을 전부 먹는다. **구조보존 큐레이션이 이 질문에서 졌다.**
   2홉 질문에서 답을 담은 엣지가 1홉 잡음에 밀리는 것은 우리 설계의 결함이고,
   이 문서의 논지가 자랑하는 바로 그 부품이다.
3. **개체 접지 검사는 그 실패를 못 봤다.** 옛 답은 컨텍스트에 있던 **고객사**를
   나열했고 — 질문이 요구한 개체 타입이 아니다 — 그 이름들이 컨텍스트에 있었으므로
   당시 접지율 **19/19 = 100%** 를 통과했다.

**「접지됐다」는 「맞다」가 아니다.** claim 단위 접지와 완전성을 따로 두는 이유가
이것이고, 그마저도 **질문이 요구한 개체 타입을 답이 맞췄는지**는 보지 않는다.

새 모델의 거부는 **주어진 컨텍스트 기준으로 옳다** — 없는 것을 지어내지 않았다.
접지 분모가 `19/19` → `18/18` 로 준 것은 품질 저하가 아니라 정당한 거부가 하나
늘어서다. 다만 **거부가 옳다는 것이 시스템이 옳다는 뜻은 아니다.**

지금 우리가 못 재는 것을 여기 적어 둔다 — 재지 않은 것을 잰 것처럼 두지 않는다.

**새 지표와 기존 지표의 관계.** 기존 hit@5, execution match, recall은 레인별 검색 품질로 유지하되, 헤드라인은 **다단계 완료율 + claim 접지 + 완전성**으로 바꾼다. 업계의 현재 관행과 맞추고, 심사자가 "종단으로 실제로 풀리는가"를 바로 본다.

## 0.14 라우팅 일반화 — 홀드아웃 두 벌과 그 사이에서 무너진 것

**왜 쟀나.** 라우팅 30/30은 사업자가 공개한 예시 문항 기준이고, 라우터 어휘를 그 문항을 읽으며 작성했다. 즉 in-sample이다. 사업자는 "평가는 공개 예시와 **비슷한 기준**"이라고 했고, 기능테스트는 외부 기관이 자기 말투로 묻는다. 그래서 라우터가 보지 않은 문구로 두 번 물었다.

### 평가셋이 공정한가가 먼저다

두 생성기 모두 검증을 통과하지 않으면 기록하지 않는다.

- 라벨은 평가자가 보고 맞춘 것이 아니라 **데이터 구조**가 정한다. 컬럼이 답하면 nl2sql, 문서가 답하면 vector_search, 엣지가 답하면 knowledge_graph다.
- 고유명사는 데이터셋에 실재하는 것에서 다시 뽑는다.
- 2차는 공개 30문항·1차와 **고유명사를 마스킹한 뒤 8자 이상 겹치면 거부**하고, **온톨로지 엣지 7종을 전수 포함**한다(1차는 4종에 몰려 있었다).
- 지표는 손으로 적지 않는다. 기대 레인의 도구가 라우터의 실제 `tools` 배열에 있는지로 코드가 판정한다.

### 결과

「규칙만」 열과 coverage, true_miss 는 2026-08-19 의 값이다. 「현행」 열은 규칙 게이트와 시맨틱 폴백을 넣은 뒤의 재측정인데, 이 두 세트는 진단에 써서 개발용이다(§0.15).

| 평가셋 | 현행 strict (09-30) | 규칙만 strict (08-19) | coverage | true_miss |
|---|---|---|---|---|
| in-sample 30 (공개 예시) | 30/30 | 30/30 | 1.000 | 0 |
| 홀드아웃 1차 (템플릿 문형) | 1.000 | 0.900 | 1.000 | 0 |
| **홀드아웃 2차 (업무 담당자 구어체)** | 0.967 | **0.633** | 0.933 | 2 |

`strict`는 라벨 문자열 일치, `coverage`는 기대 레인에 실제로 닿은 비율, `true_miss`는 닿지도 못한 것이다. fan-out으로 기대 레인을 함께 연 경우는 답이 나올 수 있으므로 라벨 불일치와 같은 실패로 세지 않되, 정답으로 합치지도 않는다.

### 읽는 법 넷

1. **세 숫자를 섞지 않는다.** (08-19, 규칙만) 30/30은 공개 예시, 0.900은 템플릿 문형, 0.633이 구어체다. 헤드라인으로 쓸 수 있는 것은 가장 낮은 것뿐이다. <!--metric-ok-->
2. **1차와 2차의 간격이 평가셋의 문형이 만든 착시다.** 1차에서 0.900을 받고 만족했는데, 문형을 구어체로 바꾸자 같은 라우터가 0.433으로 떨어졌다. 평가셋을 의심하지 않으면 좋은 수치는 자기기만이 된다. *(0.433 은 **타입쌍 추론 도입 전** 값이고, 그 수정 후 현행은 0.633 이다 — 위 지표 표를 본다.)* <!--metric-ok-->
3. **원인은 어휘 부족이 아니라 관계 표현의 무한성이다.** "관여하는/연결된/끼고 있는/붙어 있는/창구/윗선" — 규칙 기반 라우터가 이것을 사전으로 따라잡는 것은 원리적으로 진다. 그래서 관계어를 맞히는 대신 **개체 타입 쌍을 온톨로지 엣지에 대조**하는 방식으로 바꿔 0.433 → 0.633, knowledge_graph는 1/10 → 7/10이 됐다. 늘어나는 어휘는 노드 타입 지시어뿐이고 노드 타입은 닫힌 집합이다.
4. **타입쌍은 한계를 늦춘 것이지 없앤 것이 아니다.** 남은 true_miss 2건도 그대로 공개한다. `지난 분기 회고에서 나온 개선 안건 뭐였지?`는 시간 표현이 구조화 신호로 잡혀 nl2sql로 샜고, `고객사를 제일 많이 끼고 있는 사람이 누구지?`는 실재 개체명이 없어 타입쌍이 발동하지 못했다.

### 두 홀드아웃은 이제 홀드아웃이 아니다

1차는 온톨로지 커버리지 구멍(PR #14)을, 2차는 타입쌍 부재(PR #15)를 **진단하는 데 썼다.** 진단에 쓴 순간 그것은 홀드아웃이 아니고, 수정 후의 수치는 "고친 것이 고쳐졌다"는 확인이지 일반화의 새 증거가 아니다. 다음 표면형 계열은 3차에서 잰다. 이 문단을 지우지 않는 이유는, 이 구분을 흐리는 순간 위의 표가 광고가 되기 때문이다.

### 재발 방지

`router.test.ts`가 `edges.json`을 읽어 **모든 엣지 타입에 라우팅 신호가 있는지** 검사한다. 라벨을 손으로 적지 않으므로 데이터셋에 관계가 추가되면 라우터를 고치기 전에 테스트가 먼저 깨진다. 실제로 `HAS_PROJECT`(354엣지 중 40)가 신호 없이 방치돼 있었고, 그것이 1차 0.767의 절반을 설명했다.

## 0.15 멘토링 기간 라우팅 개선: 규칙 게이트, 시맨틱 폴백, 봉인 홀드아웃 두 번

**계기.** 리원에이스 멘토링 회신(2026-09-22)이 채점 관점을 알려 줬다. 최종 답변이 정답과 맞는지가 기본이고, 라우팅은 그 선행 지표이며, 구어체 라우팅을 올리는 것이 답변 품질을 올리는 가장 효율적인 경로라는 것이다. 제안은 넷이었다. 시맨틱 폴백의 앵커 확대, 신호 가중치 합산과 1위, 2위 격차 게이트, 규칙과 시맨틱의 경계를 홀드아웃으로 실측, 오분류 패턴 분석. 넷 다 넣었다.

### 설계

- **가중치 합산.** 사다리(§0.14의 규칙)는 첫 일치에서 멈춰 「얼마나 확실한가」를 버렸다. 같은 신호를 도구별 점수로 합산한다. 관계 동사 3, 문서 어휘와 타입쌍 2, 개체에 걸린 관계 명사 1.5, 정형 신호와 의미 신호 개당 1. 사다리가 고른 도구의 점수에서 나머지 중 최고점을 뺀 값이 격차다. 감사 로그에 `rule_scores`, `rule_margin`, `rule_confident` 로 남는다.
- **격차 게이트.** 격차가 `RULE_MIN_MARGIN`(2.5) 미만이거나 규칙이 판단을 포기하면(hybrid) 시맨틱 폴백으로 넘긴다.
- **시맨틱 앵커.** 질문 유형 35가지(nl2sql 14, vector_search 14, knowledge_graph 7)에 같은 뜻의 표현(구어체, 줄임말, 어순)을 5개씩, 175문장을 둔다. 유형은 실패 문구가 아니라 데이터 구조에서 뽑았다. 테이블마다 집계와 조회, 문서 유형 넷의 섹션 제목마다 세부, 엣지 타입 일곱마다 하나. 비교 전에 온톨로지 개체명과 하루 날짜를 타입 자리표시(`{제품}`, `{날짜}` 등)로 가린다. 최근접 앵커의 도구를 고르고, 1위와 2위의 유사도 차가 `SEMANTIC_MIN_MARGIN`(0.02) 미만이면 규칙의 넓은 fan-out 을 유지한다. 그래프로 보낼 때는 최근접 앵커의 유형 이름(= 엣지 타입)이 탐색 계획이 된다.
- 임베딩은 서버가 이미 쓰는 bge-m3(768 절단)다. 생성 모델 호출은 없다. 임베딩 모델이 없으면(해시 임베더, 오프라인 테스트) 폴백은 설치되지 않고 규칙만 돈다.

### 측정 규약: 고치기 전에 봉인하고, 고친 뒤 한 번만 잰다

앞선 두 홀드아웃은 진단에 쓰는 순간 홀드아웃이 아니게 됐다(§0.14). 이번에는 절차로 막았다.

1. 라우터 코드, 결과 파일, 앞선 오답을 보지 않은 **다른 모델**에게 데이터셋만 주고 60문항(도구별 20)과 정답 근거(정답 SQL, 문서, 엣지)를 쓰게 한다.
2. 그 파일을 **라우터를 고치기 전에 커밋**한다(홀드아웃3 `f597483`, 홀드아웃4 `ee53a9d`). 커밋 전에 내용을 열어 보지 않는다.
3. 고친 뒤 **한 번** 채점한다. 오답을 분석하는 순간 그 세트는 개발용으로 내려간다.

홀드아웃3은 GPT 계열, 홀드아웃4는 Kimi 가 썼다. 정답 SQL 40개는 전부 실행되고 빈 결과가 없다.

### 홀드아웃3 오답이 가리킨 것

### 「튜닝 0」 주장을 고쳤다

종전 문서는 라우터가 LLM 호출 0, 튜닝 파라미터 0이라고 적었다. 지금 라우터는 생성 호출은 여전히 0이지만 임베딩 모델을 한 번 부르고, 튜닝 값이 둘 생겼다(두 격차 경계). 값은 위의 경계 실측 파일이 정하고 배포마다 조정하지 않는다. 결정론은 「같은 임베딩 모델이면 같은 결정」으로 좁혀 적는다. 같은 가중치의 bge-m3 를 도커 컨테이너(CPU)와 호스트에서 각각 돌려 홀드아웃3 60문항의 결정이 전부 같았다. 해당 주장은 README, 결과보고서, 이 문서 §0, §2 에서 함께 고쳤다.

### 서버 사전과 평가 사전이 달랐다 (2026-10-02)

멘토 예시 「서울 쪽 매출이 어때」(nl2sql)를 서버 경로로 돌리자 그래프로 갔다. 서버의 개체 사전(DB 개체명과 별칭, 296개)에 이름이 아닌 속성 값 32개가 들어 있었다. companyx 적재기는 `ontology.search` 가 속성 값으로도 개체를 찾도록 지역 8, 업종 10, 직급 6, 제품 범주 4, 프로젝트 상태 4를 별칭으로 넣는데, 라우터가 그것을 개체 이름으로 받아 「서울」을 `{고객사}`로 가렸고, 「{고객사} 쪽 매출이 어때」가 그래프 앵커 「{고객사} 쪽 일 뭐 하고 있어」에 붙었다. 앵커는 지역과 업종을 글자 그대로 쓴다(「서울 매출 얼마야」, 「제조업 고객사 명단」).

평가가 못 잡은 것은 사전의 출처가 둘이어서다. 라우팅 평가 CLI 는 데이터셋 그래프 노드 이름(131개)으로, 서버는 DB 로 사전을 만든다. 둘을 대조하는 통합 테스트(`ontologyload.test`)는 홀드아웃 2차 30문항의 규칙 결정만 봤다.

- **고친 것.** 별칭은 한 개체만 가리킬 때 이름으로 넣는다(`identifyingAliases`, 서버 사전 264개). 여러 개체가 나눠 가진 값은 속성이다. 대조 테스트는 문서가 인용하는 문항 세트 전부(278문항)에서 규칙 결정과 시맨틱 단계 입력(마스킹)을 함께 본다. 둘이 같으면 최종 결정도 같다. 고치기 전 코드로 돌리면 이 테스트가 20문항 불일치로 실패한다.
- **수치 영향.** 위 표의 라우팅 수치는 평가 사전으로 잰 것이고, 고친 서버 사전에서도 278문항의 결정이 모두 같다. 고치기 전 서버 사전에서는 3문항이 다른 경로로 갔고 셋 다 틀린 쪽이었다(봉인 홀드아웃4 「부산 쪽에 있는 IT/SW 업종 고객사가 어디였더라?」가 SQL 레인 없이 그래프로, 벡터 정답셋의 제안서 질문 둘이 그래프로). 서버 경로로 잰 답변 수치 가운데 사업자 30 최종 답(28/30), `ask`, 그래프 정답셋은 경로가 바뀌는 문항이 없어 그대로다. 봉인 홀드아웃4 답변 채점(27/59)은 고치기 전 서버로 잰 1회 기록이고, 59문항 중 위 한 문항의 경로가 바뀐다. 봉인 규약대로 다시 채점하지 않는다.
- **멘토 예시 넷.** 「서울 쪽 매출이 어때」(nl2sql), 「김민준이 하는 일」(knowledge_graph), 「Product-C1 어떻게 깔아」(vector_search)는 기대대로 간다. 「매출 관련 보고서」(vector_search)는 nl2sql 로 간다. 규칙은 문서 어휘로 vector_search 를 골랐지만 격차가 2라 시맨틱에 넘겼고, 시맨틱이 「지난 분기 매출 합계」에 붙었다. 이 데이터의 문서 40건 본문에 「매출」은 한 번도 나오지 않는다. 고치려면 앵커나 경계를 건드려야 하므로 새 봉인 세트로 잰다.

### 스키마 카드, 도구 선택, 컨텍스트 예산 (2026-09-30, 호스트 GPU 개발 측정)

위 표는 라우팅(선행 지표)이다. 채점 기준인 최종 답 일치는 채점표(`npm run companyx:score`, 봉인 세트는 `CX_SET=holdout3|holdout4`)로 잰다. 판정은 LLM 심판 없이 답 문자열과 정답 파일만 본다(`air-server/src/scorecard.ts` 머리말). 아래는 결정을 내리려고 호스트 GPU 에서 잰 개발 측정이고, 정본 수치는 컨테이너 CPU 측정이다(§9).

- **스키마 카드 인라인 주석**(멘토 제안). 질문이 묻지 않은 id 열을 뺀 실행 일치로 개발용 홀드아웃3 정형 20문항 주석 11 대 한 줄 9, 사업자 10문항 7 대 7. 봉인 홀드아웃4 정형 20문항 1회 13 대 8. 기본값을 주석 카드로 바꿨다(`SQL_CARD=compact` 가 종전 카드).
- **0행 수리.** 결과가 0행이면 한 번 고쳐 보고, 고친 쿼리가 행을 돌려줄 때만 쓴다. 개발용 11 → 12, 퇴보 없음. 기본값으로 켰다(`SQL_EMPTY_REPAIR=0` 이 끈다).
- **생성 모델.** 개발용 30문항에서 qwen2.5-coder:7b 18, qwen3.5:9b 20, gemma4:e4b 19. 미리 정한 교체 기준(+3)에 못 미쳐 유지했다.
- **LLM 자율 도구 선택 대 규칙 라우터**(멘토 제안, `npm run companyx:toolselect`). 같은 7B 에게 MCP tools/list 설명만 주고 고르게 하면 봉인 홀드아웃4 38/60, 규칙만 45/60, 규칙+시맨틱 54/60. 개발용 150문항 113 대 109 대 145. 7B 는 선택 150건 중 148건을 tool_calls 가 아니라 본문 JSON 으로 냈다.
- **컨텍스트 예산.** 서버와 같은 라우터 상태로 개발용(사업자 30 + 홀드아웃3 채점 가능 38) 정답 합이 256: 39, 512: 41, 1024: 44 라 기본값을 1024 로 올렸다(`pipeline.ts` `DEFAULT_BUDGET`).

원자료(`eval/results/`): 스키마 카드 `companyx-sql-llm-holdout4.json`(주석), `companyx-sql-llm-compact-holdout4.json`, `companyx-sql-llm-compact-holdout3.json`, 0행 수리 `companyx-sql-llm-emptyrepair-holdout3.json`, 생성 모델 `companyx-sql-llm-qwen3.5_9b-holdout3.json`, `companyx-sql-llm-gemma4_e4b-holdout3.json`, 도구 선택 `companyx-toolselect.json`, `companyx-toolselect-holdout4.json`, 컨텍스트 예산 `companyx-scorecard-b{256,512,1024}.json`, `companyx-scorecard-holdout3-b{256,512,1024}.json`.

## 2. 왜 이 설계가 "복잡도↓·장애 지점↓"인가 (리원에이스 핵심 가치)

**(1) 튜닝 최소 — 설정 민감성 제거.** 라우팅은 규칙 우선(생성 호출 0)이고, 규칙이 확신하지 못한 질문만 임베딩 앵커로 넘긴다. 튜닝 값은 그 격차 경계 둘이며 개발용 150문항의 경계 실측이 정한다(§0.15). RRF 융합·구조보존 큐레이션·벡터 tie 정렬은 전부 결정론. 테스트가 run-to-run **분산 0**을 단언한다. → 리원에이스 논지("튜닝 파라미터 9→2")를 코드로 실증. (NL2SQL·최종답변만 7B라 비결정론이며, 이는 명시적으로 표기.)

**(2) 장애 지점↓ — 다층 방어.**
- **air 플러그인**: timeout / retry / circuitBreaker를 전역 적용(운영 기능을 직접 짜지 않음 = 코드 복잡도·버그 표면↓).
- **병렬 fan-out**은 `Promise.allSettled` + `branch_errors` 감사 → 한 브랜치가 죽어도 크래시 없이 부분 컨텍스트 반환.
- **장애주입 스위트**로 실측(§4).

**(3) air 관용적 활용 + 학술 근거.** `defineServer`/`defineTool` + 플러그인 + Pylon-7 `layer` 힌트(인용→구현). 컨텍스트 구성은 전현우 외 2026(TACC) — "무조건 많이가 아니라 모델·과업에 맞게 선별" — 을 L4 설계 근거로 삼음.

## 3. 아키텍처 (레이어)

- **L1 substrate** — PostgreSQL 16 + pgvector. 스모크 시드(public)와 콘테스트급 벤치(`bench` 8테이블) 분리.
- **L2 데이터 도구** — `sql.query`(읽기전용 트랜잭션 + 최소권한 `mcp_ro` 강등 → `pg_read_file` 등 superuser 함수·쓰기 거부, statement/lock timeout), `vector.search`(pgvector 코사인, BGE-M3, id 2차정렬로 tie 결정성, k 클램프).
- **L3 결정론 라우터(MCP Parallel)** — 규칙 기반 한국어 질의 분류(LLM 0, 튜닝 0, 분산 0) → structured/semantic/hybrid 병렬 fan-out + 감사 로그.
- **L4 구조보존 큐레이션(TACC)** — 스키마인지 row 원자 패킹(`broken_rows=0`). 해자 = 고정예산에서 **SQL 튜플을 안 깨고** 트림(naive 토큰컷의 실패모드 회피).
- **L5 온톨로지/지식그래프** — `entities/aliases/relations/entity_links`. `ontology.search`(별칭 해소: 전자제품→전자기기), `graph.expand`(타입 관계 BFS + provenance, 홉·노드·엣지 상한 `GRAPH_MAX_HOPS`/`GRAPH_MAX_NODES`/`GRAPH_MAX_EDGES` — 걸리면 예외가 아니라 `truncated`).
- **L7 답변** — 온프렘 Qwen2.5-Coder-7B(Ollama). 큐레이션 컨텍스트에만 근거, 근거 없으면 거부.
- **융합** — canonical `entity_links` 브릿지로 SQL/vector/graph 후보를 동일 정규 엔티티로 매핑 → **named-source RRF**(3-way agreement).

토폴로지 다이어그램: `docs/architecture.md`.

## 4. 운영 안정성 (헤드라인 — 실행 결과)

- **결정론(범위 한정):** route/RRF/curator/벡터정렬 = 분산 0(테스트 단언). NL2SQL·답변은 7B라 비결정론(명시).
- **장애주입 스위트:** `eval/results/faults.json` — 4 시나리오(vector fail / graph fail / sql fail / vector unavailable)에서 **no-crash 4/4, partial-context 4/4(≥80%), error-visible 4/4**. `branch_errors` 로깅 100%. 스위트가 실제 크래시 버그(kgRetrieve `entity_links` 조회)를 적발→수정.
- **권한 경계:** `sql.query`는 `mcp_ro` 강등 → `pg_read_file` 등 superuser 함수·쓰기·문장 체이닝 거부(`db.test`).
- **클러스터:** 무상태 air 서버 → 수평 확장 구조. 6개 read-only 도구는 `getReadPool()` 경유 — `READ_DATABASE_URL` 설정 시 읽기 오프로드, 미설정 시 Primary 투명 폴백(`db.test` 22/22).
- **검증된 라이브 read-replica spike** (`scripts/replica-spike.sh`, 로그 `eval/results/replica-spike.log`): `pg_basebackup` hot-standby → 실제 **streaming replication**(`state=streaming`), write→replica 3초 반영, replica **read-only 강제**, `getReadPool()` replica 라우팅, **kill-drill: primary 정지 중에도 replica가 reads 제공**(orders=2000)→primary 재기동 정상. **단정 안 함**: 자동 promotion/failover·lag SLA·멀티노드 부하 = production HA 범위(미수행).

  우리 NL2SQL 재시도가 정확히 그 기법이다 — 다만 **`qwen2.5-coder:7b` 에서는 재시도가 점수를 올리지 않는다**(무재시도 8/10, 재시도 8/10, 수리 0회, 2026-10-01 정본). 옛 `qwen2.5:7b` 에서는 5/10 → 7/10 이었다.
  우리가 고른 것을 독립 연구가 같은 방향으로 지지한다.
- **위협 — schema linking 은 도움이 되지 않고, gold-table recall 96.5%의 임베딩 링커도
  무링킹과 통계적으로 구별되지 않는다.** 우리는 hit@5 **0.986**짜리 검색기를 갖고 있다.
  그 결과대로면 **검색이 좋아도 SQL 정확도는 좋아지지 않는다.**

  변명하지 않고 **주장의 범위를 좁힌다.** 우리 ablation(1% / 37% / 88%, `qwen2.5-coder:7b`)은 사업자 스키마
  **8테이블 하나**에서 잰 값이고, 그 규모에서는 스키마 링킹이 자명하다 — 전체 스키마가
  프롬프트에 들어간다. 즉 그 51%p 는 「어느 테이블을 고를까」의 효과가 **아니라**
  「고른 것을 어떤 모양으로 줄까」의 효과다. 이 구분을 넘어서 일반화하지 않는다.

  그리고 실제로 **우리 BIRD 수치는 낮다.** 다중 DB·대형 스키마에서 검색이 SQL 을 구해
  주지 못한다는 그 논문의 예측과 우리 관측은 **어긋나지 않는다.**

## 8.5 무엇이 보장이고 무엇이 관측인가

**재현하기 전에 이걸 읽는다.** 이 저장소의 수치는 두 종류이고, 섞어 읽으면 맞는 값도
의심스러워 보인다.

| | 보장 (다르면 결함) | 관측 (달라도 정상) |
|---|---|---|
| **무엇** | 규칙·구조가 정하는 값 | 로컬 7B가 문자열을 만드는 값 |
| **지표** | 라우팅 30/30 · KG 재현율 · 벡터 hit@5 · 홀드아웃 1·2 · 다단계 · 장애 주입 4/4/4 · 규칙 지문 5/5 · 테스트 단언 수 | 내부 벤치 execution-match · NL2SQL · 종단 지연 · BIRD · 파이프라인 지문 |
| **재현** | `node scripts/remeasure.mjs` — 8종을 다시 재고 **값이 하나라도 바뀌면 exit 1**(테스트 단언 수는 `verify-test-counts` 가 러너로 매번 실측한다) | 같은 명령을 다시 돌리면 값이 달라질 수 있다. 그래서 remeasure는 이 셋(`ask`·`bench:internal`·`external:bird`)을 **건너뛰고 그 이유를 매번 출력**한다 |
| **실측 예** | 2026-08-18에 코드 60여 개 PR을 넣은 뒤 재측정 — **값 변화 0** | 파이프라인 지문이 08-18 에 4/5 → 3/5 → 5/5 로 흔들렸고, 모델을 바꾸자 08-19 에 세 번 다 5/5 였다. 내부 벤치는 7주 만에 83 → 81, 모델 교체로 88 |

**둘을 나눈 이유.** 지문 하나로 뭉뚱그렸으면 "가끔 비결정적"으로 읽혔을 것이다.
나누고 나면 **무엇을 약속하고 무엇을 약속하지 않는지**가 그대로 드러난다.
관측 값을 헤드라인에 적을 때는 측정 날짜와 재실행 횟수를 함께 적는다.

### 클론하면 바로 돈다 (Windows 확인)

셸 스크립트가 CRLF 로 체크아웃되면 `bash` 가 첫 줄에서 죽는다
(`set: pipefail\r: invalid option name`). shebang 파일도 인터프리터 이름에 `\r` 이
붙어 실행되지 않는다. `.gitattributes` 가 없으면 Windows 클론이 정확히 그 상태가 된다.

`* text=auto` + `*.sh|*.py|*.mjs|*.ts` 에 `eol=lf` 를 못 박고, **새로 클론해서** 확인했다.

| 시나리오 | 결과 |
| --- | --- |
| 로컬 저장소에서 `git clone` | 실행 파일 12개 전부 LF |
| **GitHub 에서 `git clone`** | 실행 파일 12개 전부 LF |
| `npm ci` → `npx tsc` | 통과 |
| 데이터셋 없이 게이트 9종 | 전원 `rc=0` |
| `bash scripts/fetch-companyx-dataset.sh` | 다운로드 → **SHA-256 일치** → 해제, 문서 40건 |
| `bash -n` (셸 스크립트 2종) | 문법 통과 |

작업 트리를 고친 것과 새 클론이 정상인 것은 다른 주장이라 둘 다 확인했고, 거기서 멈추지 않고 **심사자가 아무 준비 없이 밟는 범위 전체**(클론 → 빌드 → 게이트 → 데이터셋 취득)를 새 클론에서 한 번에 돌렸다.
`node scripts/verify-line-endings.mjs` 가 CI 에서 재발을 막는다.

### 실행 순서가 결과를 바꾸지 않는다

위 명령은 어느 순서로 돌려도 된다. 평가와 데모는 자기가 읽는 데이터를 남겨 두고 나온다.

- **DB 를 쓰는 평가는 벡터 평가 하나뿐**이다(임베더를 바꿔 가며 재현율을 재야 하므로).
  DDL 과 258행 UPDATE 를 한 트랜잭션으로 묶고, 끝나면 주 임베더 차원으로 되돌린다.
  `node scripts/drill-corpus-restore.mjs` 가 실행 전후 코퍼스를 세어 대조한다
  (실측: 258청크 · 768차원 · 258문서 불변).
- **`npm run demo` 는 DB 에 쓰지 않는다.** 실행 전후 코퍼스·시드가 동일함을 확인했다.
- 홀드아웃 평가는 **입력마다 다른 결과 파일**에 쓴다. 종전에는 출력 경로가 고정이라
  홀드아웃2 실행이 홀드아웃1 정본을 덮었고, `metrics-check` 가 그걸 잡았다.
- companyx 전용 평가는 `DATASET=companyx` 가 아니면 **거절한다**. 다른 프로파일로
  돌려 정본을 잘못된 값으로 덮는 경로를 막는다.

이 항목들은 전부 한 번씩 실제로 깨졌던 자리다. 그래서 문장이 아니라 검사로 지킨다.

### 수치가 어긋나면 무엇이 잡는가

원자료를 다시 뽑았는데 문서를 안 고치면 아래가 실패한다. 손으로 맞추지 않는다.

```bash
node scripts/metrics-check.mjs                 # 표 행 marker 대 원자료
node scripts/verify-doc-metrics.mjs            # marker 없는 표·산문까지
node scripts/verify-test-counts.mjs            # 러너 출력에서 단언 수 재계수
node scripts/evidence-manifest.mjs             # 이 절과 실제 파일의 드리프트
```

전체 목록과 각 검사가 막는 것은 README 「주장을 지키는 검사」에 있다.

- 하드웨어: Apple M4 / macOS 25.5 (초기 빌드·내부 벤치). 공식 데이터셋 실측은 Windows 11 + RTX 4070 SUPER, PostgreSQL 16.14 + pgvector 0.8.6(WSL2 Ubuntu 24.04), Ollama 0.32.14(2026-08-18 실측) — 실행 환경이 바뀌어도 같은 커맨드로 재현되는지까지 확인한 결과다.

### 이 표가 지목하는 것

**최대 갭은 성능이 아니라 외부 참여다** — 단 2026-08-20 공식 배점이 그 칸을 10에서 5로 낮췄고, 그만큼을 오픈소스SW 적절성(10 → 15)에 옮겼다. 갱신된 가중치에서 우리의 미충족 항목은 작아지고 이미 충족한 항목(의존성 라이선스·SBOM·정상 운영)이 커졌다. 그래도 외부 참여가 0이라는 사실은 그대로 적는다. 저장소 공개와 이슈/PR 운영은 닫혔다 — 커밋 530, PR 240(병합 221), 이슈 15, 릴리스 2, CI 검사 20종이 매 PR 마다 돈다. `main` 은 상태 검사 3종을 필수로 요구하고 **`enforce_admins` 를 켜 관리자에게도 적용**한다(2026-08-18 에 일부러 빨간 PR 을 만들어 `405: 2 of 3 required status checks have not succeeded` 로 차단되는 것을 확인했다). 병합된 브랜치는 정리해 `main` 하나만 남긴다.

  남은 갭은 **star 0 / fork 0 / 외부 PR 0** 이다. 이건 우리가 만들 수 없는 수치이고 지어내지도 않는다 — 표지판(good first issue 2건, Discussions, CONTRIBUTING 의 「내 데이터에 붙이기」)을 세워 두고 **없다는 사실을 그대로 적는다.**
